# UI：臺中餐廳＋公車推薦介面

Streamlit 單頁介面，對應 DESIGN.md §5 模組 9「輸出與互動」。使用者填寫需求後，右側顯示推薦餐廳、評論依據、公車方案與 T／F／U 判定。

**狀態**：已能串接API（`api/server.py`），也可切換成 mock 資料。店家資料目前是示意資料，離線模式下的路線也不是真的。

資料格式**以`api/API.md` 為準**，本資料夾不另訂契約；`backend.py` 負責把 API 回應轉成 UI 用的結構。

## 執行

在 repo 根目錄：

```bash
pip install -r ui/requirements.txt
streamlit run ui/app.py
```

需要 Python 3.10 以上與網路連線（地圖圖磚來自網路）。已用 Python 3.12、Streamlit 1.50 測試。

### 串接API

1. 另開一個終端機啟動後端（細節見 `api/API.md`）：
   ```powershell
   $env:PYTHONUTF8 = "1"      # Windows 中文環境建議；pip 讀 requirements.txt 的中文註解會因 cp950 失敗
   cd api
   pip install -r requirements.txt
   python server.py           # http://127.0.0.1:8000
   ```
2. 在 UI 側邊欄把「資料來源」改成「API」，**保持「離線模式」勾選**。
3. 離線模式不查 TDX、馬上回傳，路線是同一份樣本；關閉會真的查 TDX（每家候選約 13 秒、免費方案每分鐘 5 次，出發時間必須晚於現在）。
4. 不要頻繁使用一句話解析（`/parse`），Gemini 免費方案一天只有 20 次；目前 UI 還沒接這個功能。

## 檔案

| 檔案 | 說明 |
|---|---|
| `app.py` | 介面本體：左欄輸入、右欄結果、側邊欄切換資料來源 |
| `backend.py` | 唯一的資料接點 `get_recommendations()`：取得 mock 或 API 回應，轉成 UI 結構；`ApiError` 表示後端失敗 |
| `mock_result.json` | 假資料，`/recommend` 回應格式（見下方情境表） |
| `requirements.txt` | streamlit、folium、streamlit-folium（API 呼叫用標準函式庫，不需額外套件） |

## 功能

**輸入（左欄）**
- 情境（DESIGN §9.1 標籤表）、出發地（地圖點選＋快速選擇）、出發日期時間（預設明天 19:00）
- 預算：每人或整團。後端只收每人預算，整團時 UI 會換算（無條件捨去）並顯示提醒
- 進階設定：單段步行上限、用餐時長（不指定則由後端標示為假設）、召回家數

**結果（右欄）**
- 後端的 `notes` 逐則照原文顯示
- 推薦卡片：情境符合度、評論引文（含面向／標籤徽章）、公車時間線（出發、到店、離店）、條件徽章、可展開的判定原因、原影片連結
- 反證（負評）收合顯示；通過事實查核的 AI 說明才顯示
- 「不確定」與「不通過」預設摺疊；三組全空時顯示後端給的原因
- 條件徽章依 `checks` 逐項渲染，不寫死項目；遇到沒看過的項目 key 會直接顯示 key
- 後端失敗（HTTP 400／500、連不上）顯示錯誤訊息，429 另加提示

**地圖**：點擊更換出發地；縮放、拖曳不觸發重跑；進入／離開全螢幕時標記置中。圖磚為 Esri World Street Map（免金鑰，須標示來源）。

## 轉換規則（`backend.normalize()`）

| API 回應 | UI 怎麼處理 | 原因 |
|---|---|---|
| `recommended`／`uncertain`／`rejected` | 顯示為「推薦／不確定／不通過」 | 沿用命名 |
| `checks` 是物件（budget、transit、hours） | 轉成 list，加中文標籤 | 之後新增項目不用改版面 |
| 被判 F 的店，其餘 U 的項目 | 標為「未查」（灰色），不當成不確定 | 實測：F 的店 `transit` 是 U「未查（其他條件已不符）」，`hours` 是 U「營業時段內來得及，待查公車」，不是真的不確定 |
| 非 F 的店，`reason` 以「未查」開頭的 U | 同樣標為「未查」 | 同上 |
| 其餘 U 的 `reason` | 列為「未知」警示 | 例如查不到價格 |
| `evidence` 開頭的 `【面向｜標籤】` | 拆成徽章與引文 | `API.md` 說明可拆；示意資料沒有這個前綴 |
| `explanation` | 只有 `explanation_source == "llm"` 才顯示 | `template` 只是把引文、路線、預算、營業串成一句，卡片上已有，會重複 |
| `sections[].from`／`to` 為 `null` | 第一段起點補「出發地」、最後一段終點補餐廳名 | API 對出發地與餐廳給 `null` |
| 離店時間 | 到店時間 + `request.meal_min` | API 沒有離店時間 |
| 總旅行分鐘 | 直接用 `travel_min` | 各段分別四捨五入，加總會差 1 分（實測 1+14+8=23，`travel_min` 24） |
| 三組全空 | 顯示最後一則 `notes` 為原因 | 有候選但被淘汰的店會在 `rejected`，所以全空 = 沒有情境相符的店 |
| 整團預算 | `floor(總額 ÷ 人數)` 後送出，並加一則提醒 | API 只收每人預算整數 |

## relevance 分級（暫定，待與組員討論）

`relevance` 是 BM25 分數除以理論上限、夾在 0–1。數值天生偏低：實測示意資料查「慶生」只有 0.32、0.33、0.37。若直接顯示數字或星等會誤導使用者（看起來像「只符合三成」），所以 UI 改顯示等級：

| 等級 | 條件 | 常數（`backend.py`） |
|---|---|---|
| 高 | ≥ 0.6 | `RELEVANCE_HIGH` |
| 中 | ≥ 0.3 | `RELEVANCE_MID` |
| 低 | < 0.3 | — |

**這兩個門檻是我憑少量實測值暫訂的，沒有根據**，需要討論：
1. 要不要顯示等級，或乾脆不顯示。
2. 門檻怎麼定：召回方法（bm25／vector／hybrid）不同，分數分布不同。向量餘弦的無關店也有 0.60–0.68（見 `prototype/README.md`），同一組門檻套在不同方法上不合理。
3. 是否由後端直接提供等級，避免前端猜測分數的意義。

## Mock 情境

側邊欄「Mock 情境」切換。**實測**表示回應取自 2026-11-20 以 `offline: true` 呼叫 `/recommend`（店家為 `prototype/restaurants.json` 的示意資料）；**推導**表示依程式與 `API.md` 手寫，非實測，檔案內標有 `_derived`。

| 情境 | 來源 | 說明 |
|---|---|---|
| `all_kinds` | 實測 | 預算 600：1 間推薦、2 間不確定 |
| `budget_low` | 實測 | 預算 200：無推薦、2 間不通過（含「未查」項目）、1 間因缺價格仍不確定 |
| `no_candidates` | 實測 | 情境「火星料理」：三組全空 |
| `tdx_429` | 推導 | TDX 失敗：`route` 為 null、交通 U；依 `proto.py`，營業項由 `server.py` 補成 U「未查核」 |
| `rich` | 推導 | 示意資料沒有的欄位：地址、原影片、反證、面向標籤、LLM 說明、轉乘路線、交通 F |
| `http_400` | 推導 | 欄位錯誤的 HTTP 400 |
| `backend_down` | 推導 | 連不上後端 |

## 待確認

1. **進度回報**：API 一次回傳，真的查 TDX 時五間店超過一分鐘，UI 只能顯示轉圈。要顯示進度需要後端串流（例如 SSE）。
2. **`checks` 會不會增加**（步行、轉乘、候車）：UI 用迴圈渲染，加項目不會壞，但要補中文標籤。
3. **`relevance` 的意義與分級**：見上節。
4. **補充偏好、轉乘上限**：UI 的「補充偏好」目前沒有後端欄位可送；DESIGN 有轉乘上限（`N_max`），API 沒有，所以 UI 已移除這個輸入。
5. **一句話輸入（`/parse`）**：UI 尚未接，要接的話需要後端的 `GEMINI_API_KEY` 與額度安排。
6. **真實資料**：`corpus/restaurants.json` 不在 git；有真實資料後，`sources`、`address`、面向標籤才會有內容，UI 這部分只以推導樣本測過。
7. **路線被判 F 時 `route` 會不會保留**：目前樣本中 F 的店 `route` 都是 `null`，我不確定交通 F 的店是否可能有 `route`，UI 兩種情況都能處理。

## 已知限制

- **UI 不會幫使用者補欄位**：缺條件的補問目前靠表單必填，尚未接 `/parse`。
- **欄位驗證有限**：檢查情境、預算，以及非離線模式的出發時間；座標範圍由後端驗證（回 400 後 UI 顯示訊息）。
- **無進度顯示**：只有轉圈文字。
- **無地址搜尋**：出發地只能點地圖或快速選擇。
- **未做**：結果中的路線地圖（API 已有 `from_location`／`to_location` 可畫）、「放寬條件再查」、手機版調整。
- **推導樣本未經實測**：`tdx_429`、`rich` 是依程式推導，後端行為若不同，以實測為準。
- **圖磚條款**：Esri 圖磚用於原型；正式上線前須再確認。第三方免費圖磚可能隨時改為需金鑰。
- **測試**：以 Streamlit AppTest 載入全部 mock 情境確認無例外；以真的伺服器（離線模式）驗證轉換結果與 mock 一致。地圖互動（點擊、縮放、全螢幕）未自動化測試。
